The Cosmos Goal-Conditioned Policy

A visual map of the model: what the pieces are, how data flows through them, and how to run it.

We reframe autonomous photography as counterfactual visuomotor policy learning. To frame a shot, the camera must imagine what the scene looks like from viewpoints it hasn't occupied yet. So the model jointly imagines the next frame, predicts a camera action, and estimates how close it is to the goal — all conditioned on a shot-profile goal.

1 · The big picture

One model, built on the frozen-or-finetuned Cosmos-Predict2.5-2B video backbone, takes the current view and a goal and produces three things at once with a single diffusion (flow-matching) process:

WORLD

Predicts the next frame (what the camera will see after the move). This is the "imagine before you act" inductive bias.

ACTION

Predicts a chunk of 8 future camera moves (Δposition + Δorientation), ALOHA-style.

VALUE

Predicts how far the current view is from the goal framing (a geometric distance).

The key idea you keep coming back to: the goal is a shot profile (a small, geometric, scene-agnostic vector — "subject this big, this far off-center, camera at this angle"), not a target image or a text prompt. Every random camera trajectory in the data is relabeled, after the fact, with the framing it happened to achieve. That turns aimless rollouts into goal-conditioned supervision for free (hindsight relabeling).

Data is generated entirely in Blender, then enriched and reshaped. Stages 1–3 produce the on-disk dataset; the policy loader (stage 4) turns it into model tensors.

3 · What one training sample is

A sample is one 8-step window sliding along a single 32-frame trajectory (so it touches 9 poses: a start, 7 intermediates, an end). The goal, crucially, is sampled further out.

frame tSTARTstate image
t+1…t+7midposes only
t+8ENDnext-state image
drawn ~ U[t+8, 31]GOALprofile + value

The 8 actions and the next-state image are anchored to the window (they're the consequence of moving). The goal is drawn from anywhere at-or-after the window end — its profile and the start→goal distance are what condition/supervise the policy.

FieldShapeWhat it isAnchored to
state_image3×H×WCurrent view (window start), in [−1, 1]window start
next_state_image3×H×WView after the 8 moves (world-model target)window end (t+8)
action_chunk8×5The 8 consecutive camera deltas, normalizedwindow (t→t+8)
goal_vec goal8Shot profile of the drawn goal frame, normalized to [−1,1]sampled frame
value_target valuescalar−geometric distance(start pose → goal pose). Always ≤ 0.sampled frame

HER-"future" goal relabeling

The goal frame is drawn uniformly from [end_frame, 31] on every __getitem__ (config: data.goal_sampling: uniform_future). This is the Hindsight Experience Replay "future" strategy — it decouples the goal horizon from the 8-step action horizon, so the value head and conditioner see goals at every distance, matching what they'll face at inference. goal_sampling: "end" restores the legacy fixed-offset behavior. Goal candidates that hit the scorer's off-screen sentinel are excluded; windows with no valid candidate are dropped.

Sign of the value: value_target is the negative distance (0 = the start already achieves the goal framing, more negative = farther). "Higher value = better," the standard convention. The positive value= you see in the training log is the value head's MSE loss, a different number.

4 · Architecture (how it predicts)

VAE encodestate & next-state frames → 16-channel latents (Wan VAE, frozen).
→
Assemble latent sequenceimage latents + 1 action latent + 1 value latent.
→
Goal conditionergoal vector → 4 "goal tokens" added onto a fixed text anchor → cross-attention.
→
Cosmos transformerone flow-matching pass denoises the whole sequence jointly.
→
Read offextract action chunk & value from their latent positions.

There are no separate action/value MLP heads. Action and value are encoded as extra "frames" inside the same latent video that the backbone already knows how to denoise. This is the cosmos-policy pattern — see the next section.

5 · The latent sequence trick

The model's "input/output" is a single latent video of T_img + 2 frames. The backbone predicts a velocity over all of them; we split the loss by position.

pos 0image
pos 1 … T_img−1image
pos T_imgACTION
pos T_img+1VALUE

world loss = MSE over the image positions  ·  action loss = MSE over the action position  ·  value loss = MSE over the value position.   total = Σ λ·loss (all λ=1 by default).

How action/value get into a "frame"

Pure tile-and-reshape, no learned parameters (action_latent.py):

  • Inject (train): flatten the 8×5 action chunk, tile it to fill the C×H×W latent frame. The value scalar is broadcast across the whole frame.
  • Extract (inference): split the denoised frame back into its repeated tiles and average them — the repetition gives many noisy estimates of the same chunk to average over, which stabilizes the readout.

6 · The goal conditioner

How an 8-number shot profile becomes something the cross-attention can use, without retraining a text encoder (conditioner.py):

1 · Fixed anchor

A real text encoder (Cosmos-2.5's Qwen2.5-VL) encodes one fixed drone-cinematography prompt once, offline → assets/text_anchor.pt. The text encoder is then never loaded again.

2 · Goal tokens

A learnable Linear(8 → 4·D) turns the goal vector into 4 new tokens, added onto the anchor at the positions right after its real text (originally padding).

3 · Zero-init gate

The goal tokens are scaled by a learnable gate initialized to 0 (ControlNet-style). So at step 0 the model behaves exactly like the frozen anchor; training ramps the gate up. Safe start, no shock to the backbone.

4 · Padding mask

Only the real anchor tokens + the 4 goal positions are marked valid; everything else stays masked so cross-attention ignores it.

The cross-attention input dimension is set at runtime to the backbone projection's true in_features (the Qwen stacked hidden states, 100352) — not the module-level default of 1024. The training script discovers this from transformer.crossattn_proj.

7 · Goal / action / value spaces

Goal — 8-key shot profile (goal_space.py)

KeyMeaningRange → [−1,1]
occupancyhow much of frame the subject fills0–100
body_in_frame_ratiofraction of subject inside frame0–100
cam_to_obj_azimuth_degcamera→subject horizontal angle (cyclic — linear seam at 0/360)0–360
cam_to_obj_elevation_degcamera→subject vertical angle−90–90
object_center_x / _ysubject bbox center, in pixels0–W / 0–H
bbox_x_offset / _y_offsethalf bbox width/height (a size cue), pixels0–W / 0–H

Pixel keys are not clipped on normalization — an off-frame subject deliberately reads as |value|>1 ("past the edge"). Ranges assume 1024×768 renders.

Action — 5D camera delta (action_repr.py)

(Δright, Δup, Δforward, Δyaw, Δpitch) in the previous frame's camera-local basis (Blender: +X right, +Y up, −Z forward). Translations in metres, angles in radians. Roll is dropped (drones don't roll the camera here). Per-dim normalized by ACTION_SCALE (p99 magnitudes) so metres and radians weight fairly in the L2 loss — and that scale is saved in the checkpoint so train/eval can't drift.

Value — geometric goal distance (reward.py)

value = −pose_distance(start, goal): a weight-free product metric in radians — great-circle angle on the viewing sphere (handles azimuth cyclicity + polar degeneracy) + Δ apparent size + Δ optical-axis aim. Computed from camera poses, not from the bbox score pixels (which the scorer zeroes at close range), so it's exact at every frame.

8 · Training

Flow matching (this is the "diffusion")

Matches the 2.5 checkpoint's native convention exactly:

x_t       = (1 − σ)·x0 + σ·ε          σ ∈ [0,1], sampled per batch
v_target  = ε − x0                     (velocity prediction)
v_pred    = transformer(x_t, timestep=σ, goal_condition)   # raw x_t, no preconditioning
loss      = MSE(v_pred, v_target)      split into world / action / value

σ is sampled logit-normal with forced near-noise / near-clean tails ("balanced two heads"). EDM utilities are retained for ablations but unused by default.

Why the per-iter loss looks noisy: each step draws a random σ. A near-noise batch has intrinsically high MSE across all components — that's the σ-lottery, not divergence. Trust the EMA curve (loss/total_ema) and the validation metrics, not single iterations.

Validation — built to survive the σ-noise

Fixed-σ flow loss

Every val batch evaluated at σ ∈ {0.1, 0.3, 0.5, 0.7, 0.9} with a fixed noise seed — the only thing changing between checkpoints is the model. → val/flow_loss_*

Sampler metrics

Runs the real Euler sampler and compares to ground truth → val/action_mse, val/value_mae. The actual policy-quality numbers.

Validation split — leak-safe & stable

  • Whole units, never windows. Overlapping windows share frames, so the split is by trajectory pair / placement / scene / object — never individual windows.
  • Frozen scene manifest (configs/policy/val_scenes.txt): the 4 smallest scenes (73/1945 placements ≈ 3.8%), both Forest-field assets held out together to avoid lookalike leakage. The val set is pinned forever: new data always goes to train.
  • Hash split (val_split_level: pair|placement|scene|object) for dev: assignment depends only on a unit's own name, so it's stable under dataset growth. val_names overrides it.

Multi-GPU (DDP)

torchrun is auto-detected. Effective batch = batch_size × grad_accum × nproc. Already solved: no_sync on grad-accum micro-steps, DistributedSampler + per-epoch reshuffle, rank-0 run-dir broadcast, staggered HF download, per-rank seeds, rank-0-only logging/val/checkpointing. Checkpoints store the raw (un-prefixed) policy state dict, so eval loads them unchanged. Measured on 2× A6000 48GB: frozen 0.14 it/s/rank (≈0 DDP overhead); full finetune 0.05 it/s/rank (fits 48GB only with gradient checkpointing).

9 · Inference

A single forward pass per action decision — no MPC, no planning, no candidate sampling. Flow-matching Euler sampling over σ: 1→0:

x = pure noise (B, 16, T_total, H, W)
for σ in schedule(1 → 0):
    pin image positions to the encoded current view  (clean, condition_mask=1, timestep=cond_timestep)
    v = transformer(x, timestep=σ, goal_condition)
    x = x + (σ_next − σ) · v                          # Euler step
action_chunk = average-of-tiles(x[action position]) · action_scale   # denormalized to m / rad
value        = mean(x[value position])

Standalone eval: scripts/eval_cosmos_policy.py --checkpoint … --target … --chunk_size 8 (must match training). The closed-loop Blender rollout (--render) is still stubbed.

10 · How to know if it's good

LevelSignalStatus
1 · Val metricstrain/val loss tracking; val/action_mse below a shuffled-goal baseline✅ built
2 · Value correlationpredicted value vs true pose distance (Spearman ≈ 1) — proves it understands goal geometry◻ ~30 lines to add
3 · Closed-loop rolloutroll out in Blender, re-score the final frame: final goal distance + success rate on unseen scenes, vs zero-action / random / goal-blind / action-only baselines◻ the headline number — not built
4 · World-model qualitydecode predicted next-frame latents; PSNR/LPIPS — paper figures for "imagines before it acts"◻ not built
Caveat on action MSE: diffusion policies are multimodal. If two camera paths reach the same framing (orbit left vs right), a model that picks the other valid mode scores bad MSE while being a perfectly good policy. That's why Level 3 (closed-loop success rate) is the metric that actually answers "is this a good photographer."

12 · How to run it

# 0. data: drop / symlink scored v7 placements under data/trajectories
ln -s /path/to/outputs/v7_renders/* data/trajectories/

# 1. single GPU
PYTHONPATH=. python scripts/train_cosmos_policy.py --config configs/policy/cosmos_2b.yaml

# 2. multi-GPU (one process per GPU)
CUDA_VISIBLE_DEVICES=0,1 PYTHONPATH=. torchrun --standalone --nproc_per_node=2 \
    scripts/train_cosmos_policy.py --config configs/policy/cosmos_2b.yaml

# 3. fast smoke run (short, capped samples)
PYTHONPATH=. python scripts/train_cosmos_policy.py --config configs/policy/cosmos_2b_smoke.yaml

# 4. watch it
tensorboard --logdir runs --port 6006 --bind_all

# 5. tests (no GPU / no diffusers needed)
python -m pytest tests/policy/
Outputs land in runs/<timestamp>_<run_name>/: resolved config.yaml, train.log, tb/, and ckpt_last.pt / ckpt_best.pt. Prereqs: HF login with the NVIDIA Cosmos license accepted (gated repo), and assets/text_anchor.pt present (copy it or rebuild with build_text_anchor.py). For short runs pass --warmup_iter 100 — the config's 1000 assumes a long run.
